# claude_test

Debug scripts and one-off experiments. Not part of CI.

| File | What it does | What was learned |
|---|---|---|
| `rs232_probe/baud_sweep.py` | Listen-only sweep of common baud rates on the KW-525 (`/dev/ttyUSB0`). Never writes to the port. | Only 19200 bps gives clean frames on JP4 Blue: `STX C 21000000000 56 ETX`. |
| `rs232_probe/sweep_01.log` | Output of the first sweep, machine in STANDBY. | 2400-115200 tried; 19200 is the only readable rate. |
| `rs232_probe/frames_19200_idle.log` | 10 s capture at 19200, frames grouped. | 192 identical frames, 19.2 per second; tail is a mod-256 byte-sum checksum in hex ASCII. |
| `rs232_probe/cam_standby.jpg` | Logitech C920 frame taken during the capture. | Webcam works and shows the keypad LCD (Set 2100 rpm). |
| `rs232_probe/capture_session.py` | Listen-only session recorder: logs every frame with wall-clock time (`frames.csv`), logs content changes (`changes.log`) with a webcam snapshot each, and records the webcam with a time overlay (`video.mp4`, not committed). | Camera pinned to 15 fps; the file is retimed to the measured rate so playback matches real time. |
| `rs232_probe/sessions/` | One folder per recording session. | Dry run 08:51:15: digit 8 changed `0` to `2` with no LCD change. |
| `rs232_probe/sessions/20261117_085340_step2_setpoint_edits/` | Step 2 session: EDIT, rpm edits, exit. `notes.md` and two contact sheets. | Keypad is silent in EDIT mode; after exit LCD showed 2200 rpm but frames still said 2100. |
| `rs232_probe/sessions/20261117_085806_step2b_one_edit_per_visit/` | Step 2b: one edit per EDIT visit, 10 s in STANDBY after each. `notes.md`, `sheet_standby_windows.jpg`. | LCD showed 1234 rpm, 012.3 s, ACL 04.5 in turn; frames never changed. Setpoints are not streamed in STANDBY. |
| `rs232_probe/sessions/20261117_090658_step4_vacuum_blue/` | Step 4: VACUUM on/off three times on Blue, pin 3 disconnected. `notes.md`, `sheet_vacuum_changes.jpg`. | Digit 8 = vacuum command (`2` on, `0` off). |
| `rs232_probe/sweep_02_white.log` | Baud sweep with DB9 pin 2 on JP4 White (mainboard to keypad). | 19200 bps again; frame `STX 000000000000 40 ETX`, 12 digits, no command letter. |
| `rs232_probe/sessions/20261117_091549_phaseB_white_idle_vacuum/` | Phase B on White: idle and three VACUUM cycles. `notes.md`, `lcd_vac_check.jpg`. | Characters 1-2 = vacuum reading, hex low nibble first; mean matches LCD `Vac -163`. |
| `rs232_probe/sessions/20261117_092708_step5_run_white/` | First run (5 steps ran by accident), listening on White. `notes.md`, `lcd_run_sequence.jpg`. | Characters 5-7 = speed, hex low nibble first; ramp matches ACL 5 s. Steps 2-5: field 1232 vs LCD 246, unresolved. |
| `rs232_probe/sessions/20261117_093707_step5_run_blue_1step/` | One-step run (1234 rpm, 5 s, ACL 5 s), listening on Blue. `notes.md`, `lcd_run_keypoints.jpg`. | Digits 4-7 = commanded speed (hex low nibble first); digit 8 bit 0 = run; keypad ramps the command in ~24 rpm steps every 100 ms. |
| `rs232_probe/sessions/20261117_103053_bridge_forward_first/` | First host transmit test: `bridge forward --seconds 30` on wiring B, STANDBY only. `bridge.csv`, `lcd_during_forward.jpg`. | 394 frames each way, 0 bad; all four wire paths work. Poll rate 14.0/s (was 19.2/s) with a 42 ms reply latency through the host; LCD normal. |
| `rs232_probe/sessions/20261117_103447_bridge_forward_keypad_run/` | Bench step 1: `bridge forward --seconds 150` while the operator runs a low-rpm step from the keypad. `bridge.csv`, `video.mp4` (not committed), `lcd_sequence.jpg`. | Keypad works through the bridge: 1138/1137 frames, 0 bad. Recipe 1234 rpm, ACL 5 s, 5 s: command reached 1234 rpm 4.91 s after START, measured 1230-1234 during hold, 0 rpm 0.41 s after run ended. Poll 13.5/s while running, 42 ms reply latency; the keypad ramp is timed, not counted in frames. `lcd_end_photo.jpg` (operator) shows END. |
| `rs232_probe/sessions/20261117_103946_bridge_run_2100rpm/` | Bench step 2: `bridge run --rpm 2100 --accel 5 --hold 10 --yes`, the PC drives the mainboard while the operator holds VACUUM on. `bridge.csv`, `video.mp4` (not committed), `lcd_sequence.jpg`, `vacuum_off.csv` (host vacuum-off frames sent afterwards at the user's request). | Step completed: command 2100 rpm at 4.94 s, measured 2097-2099 rpm for 9.96 s, 0 rpm 0.49 s after the step; vacuum 640-645; 0 bad frames. LCD stayed on STANDBY with Act 0 rpm; only Vac followed. The mainboard kept vacuum on with no frames arriving; a vacuum-off frame released it (643 to 0 in under 3 s). |
| `rs232_probe/abort_test.sh` | Bench abort test for the bridge: webcam, `bridge run`, optional `kill -9` of the bridge mid-run, then 30 s of `forward` so the keypad works again. One session folder per test (`*_abort_t*`). | Results are in each session row below. |
| `rs232_probe/sessions/20261117_105748_abort_t1_stop_key/` | T1: `abort_test.sh` at 500 rpm (ACL 3 s, hold 20 s); the operator presses STOP on the keypad mid-run. `run.csv`, `run.out`, `forward.csv`. | START/STOP is one key: the press started the keypad's own recipe (run on, 1234 rpm ramp). The bridge caught the frame change and stopped the spindle (492 to 4 rpm in 0.26 s), but forwarding then handed the spindle to the keypad recipe (up to 1241 rpm). Fixed with a stop latch in `forward_once`; T1 repeated after the fix. |
| `rs232_probe/sessions/20261117_110105_abort_t1b_start_stop_key_latched/` | T1 repeated with the stop latch: 500 rpm, START/STOP meant to be pressed mid-run. `run.csv`, `run.out`, `forward.csv`. | Not a valid T1: the vacuum was already on, so the run started at once and no key was pressed; the step completed (peak 514 rpm, 0 bad frames). From here on each test starts only on the operator's go. |
| `rs232_probe/sessions/20261117_110509_abort_t1c_start_stop_key_latched/` | T1 third try with the stop latch. `run.csv`, `run.out`, `forward.csv`. | Nothing started: the vacuum stayed off for the 60 s wait ("gave up waiting; nothing was started"). |
| `rs232_probe/sessions/20261117_110718_forward_between_tests/` | `bridge forward` between abort tests so the keypad works (VACUUM on before a test). `forward.csv`. | With no bridge running the keypad's VACUUM key did nothing, as expected in wiring B. |
| `rs232_probe/sessions/20261117_110816_abort_t1d_start_stop_key_latched/` | T1 with the stop latch (valid try): 500 rpm, VACUUM on beforehand, START/STOP pressed mid-run. `run.csv`, `run.out`, `forward.csv`. | Pass. The press (15.5 s into the run, 500 rpm) started the keypad's own recipe; the bridge sent a stop frame in the same poll, measured speed fell 493 to 31 rpm in 0.25 s and then 0. While the keypad recipe ran (command up to 1209 rpm, about 10 s) the latch sent stop frames and the spindle stayed at 0 rpm; the latch released when the keypad went idle. Operator confirmed the spindle stayed stopped. |
| `rs232_probe/sessions/20261117_110930_forward_before_t2/` | `bridge forward` before T2 so the operator can switch VACUUM on. `forward.csv`. | Setup only. |
| `rs232_probe/sessions/20261117_111005_abort_t2_keypad_db9_pulled/` | T2: 500 rpm, operator pulls the keypad-side DB9 mid-run. `run.csv`, `run.out`, `forward.csv`. | Pass: "keypad went quiet" 0.50 s after the last keypad frame; measured 505 to 0 rpm within 0.30 s of the stop; vacuum held at 642. |
| `rs232_probe/sessions/20261117_111117_forward_before_t3/` | `bridge forward` before T3 so the operator can re-plug the keypad DB9 and keep VACUUM on. `forward.csv`. | Setup only. |
| `rs232_probe/sessions/20261117_111146_abort_t3_vacuum_threshold/` | T3: 500 rpm with `--min-vacuum 643`, just above the resting reading, so a real reading trips the vacuum check. `run.csv`, `run.out`, `forward.csv`. | Cancelled in the countdown (reading 642); nothing turned. At rest 642 is about 14% of readings, while spinning about 22%. |
| `rs232_probe/sessions/20261117_111224_abort_t3b_vacuum_threshold/` | T3 retry, `--min-vacuum 643`. | Cancelled in the countdown (reading 642); nothing turned. |
| `rs232_probe/sessions/20261117_111327_abort_t3c1_vacuum_threshold/` | T3 third try, `--min-vacuum 643`. `run.csv`, `run.out`, `forward.csv`. | Pass: the run started (resting readings 643-649 this time) and stopped at 1.19 s, 194 rpm, in the same poll as a 642 reading. Led to `--start-vacuum` so the start gate can sit above the stop limit. |
| `rs232_probe/sessions/20261117_111608_abort_t4b_bridge_killed/` | T4b: 300 rpm, `kill -9` of the bridge 8 s into the run (PC down), `forward` resumes 5 s later. `run.csv`, `run.out`, `forward.csv`. | Killed at 11:16:23.5 while at 269-297 rpm; no frames for 5 s. The first mainboard reply after forwarding resumed read 0 rpm, vacuum 643-648: the mainboard stops the spindle on its own when frames stop, but keeps the vacuum. When within the 5 s it stopped is not in the log. |
| `rs232_probe/sessions/20261117_112308_abort_t4a_mainboard_db9_pulled/` | T4a: 300 rpm, operator pulls the mainboard-side DB9 mid-run, re-plugs after the spindle stops. `run.csv`, `run.out`, `forward.csv`. | "mainboard went quiet" 0.5 s after the last mainboard frame (284 rpm). When the cable was re-plugged the mainboard read 0 rpm with vacuum held (648); the operator saw the spindle stop on its own. Same as T4b. |
| `rs232_probe/sessions/20261117_113041_final_run_2100rpm/` | Final check before merging PR #5: `run --rpm 2100 --accel 5 --hold 10` on the final code. `run.csv`, `run.out`, `forward.csv`. | Pass: command 2100 rpm at 4.94 s, measured 2093-2099 rpm (mean 2096.3) for 9.96 s, 0 rpm 0.43 s after the step, vacuum 642-649, 0 bad frames. |
